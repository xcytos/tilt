How every control connects

One page per control group: what the buttons and sliders do, which function they call, what they write into the project document, and how they relate to the rest of the app. Cite these names in prompts (“change how setLayout clears places”) and we talk about the same line.

1. Principles the whole app obeys

  1. One document, one scene. Everything you see is rebuilt from a single JSON document. buildDoc() in js/app.js is the only writer; parseProject() in js/project.js is the only reader/validator.
  2. One reconciler. syncScene() is the only path that mounts models, converts the SET, spaces the stage and repaints the panel. Buttons never patch the stage directly — they change state, then ask for a sync or a rebuild.
  3. One writer of coordinates. applyPlaces() writes every frame’s position. Pillars have no free coordinates: frameAnchorOf() + derivePillarPlace() put them on their frame’s anchor, so a pillar can never disagree with its frame.
  4. Pure data at the bottom. layouts.js, colorways.js, recipes.js, version.js import nothing (no three.js), so the project parser runs in plain Node and the tests can too.
  5. Presets are per thing. Slider values live per model id (presets), per SET shape (setPresets), per frame’s pillars (framePillars), per frame placement (places). Nothing global hides inside a per-object control.
  6. Colour has precedence. The RGB dial (fabricColor) beats the palette chip (colorway). Theme resets the fabric; applyColorway() runs after applyPrimaryTheme() so colour always wins.
  7. Old files keep working. Legacy ids remap on load (LEGACY_MODEL_IDS, LEGACY_LAYOUT); junk falls back to defaults instead of erroring.

Four sliders Center Gap · Swing Pan · Pitch · Decline

Does
The S Curve’s whole shape: gap width, arc swing, rail tilt, slope. Arc and Slope are dials now, not objects.
Code
onParamsChange(partial, targets) → m.setParams() + scheduleRebuild()
Doc
presets[id] and, while a SET is active, setPresets[setId]
Relates
Same-id instances share one control row. With a SET active, the four numbers are saved onto that SET — switch away and back and they return. Clamped to the schema ranges in PARAMS.

Curtains toggle + fabric colour

Does
Shows/hides the drapes; under it: five board palettes, the RGB dial (0–255 ×3), and Add colour.
Code
toggle → params path; chips → setColorway(id); dial → setFabricColor(hex); button → addFabricColor(); all repaint via applyColorway()
Doc
colorway fabricColor extraColors
Relates
fabricColor (dial) overrides the palette; a palette tap or a Look clears it. Add colour appends a swatch (max 12) — the five boards are never edited. Colour re-applies after every theme change.

Look section Looks chips + Room chips

Does
One section for the whole mood: five Look chips (SET + room + palette in one tap) and, under a Room sub-label, the five rooms as chips. The twin Scene select is gone - same five items, same job, one heading.
Code
lookBlock() / chipRow(); Look → setRecipe(id), Room → setScene(id)
Doc
Look writes layout scene colorway and clears fabricColor; Room writes scene only
Relates
A Look is never stored of its own — remembered through the three fields; editing any one un-lights the chip (recipeState()). Room chips update in place through applyLive. A scene swap never moves a frame.

Placement group per frame

Does
X / Depth / Turn numbers for this one frame instance (no dragging).
Code
setPlace(key, index, patch) → savedPlaces → applyPlaces()
Doc
places
Relates
Position holds only this frame’s numbers; free numbers override the SET’s drawing; switching SET clears them (frames only). Pillars are their own group below — one subject, one box each.

Pillars group per frame · hidden until Show

Does
One group per frame, gone while the frame has no pillars. The Show check turns 0–2 pillars on/off; inside: count stepper, place (Centre / Inner ends / Outer ends), and a Look gear with the pillar’s own sliders. The pillar’s old accordion section is gone - count, place and look are one subject.
Code
pillarsBlock(id); setFramePillars(id, patch) → syncPillarsFor() rebuilds pillar:<frameId> instances; look sliders emit against the pillar instances (both move together)
Doc
framePillars + presets (pillar look)
Relates
Inner ends put the complete pair at the gap-side stand (x ±1.5 at gap 3) even while the frame pans. Overlay rows re-capture pillar places between the two applyPlaces() passes so pillars travel with frames. Render skips pillar groups’ own sections entirely (g.id !== PILLAR_ID).

Theme (footer)

Does
Light/dark room. Pole walls and sleeve height live in the frame’s Settings gear; the pillar’s look lives in the frame’s Pillars group.
Code

Doc

Relates
Theme sets a default fabric; your colour re-applies right after (applyColorway post-theme), so a palette or dial choice survives dark mode.

3. The one loop: what a click actually runs

panel event (guard: ignored while busy) → app.js setter e.g. setLayout / setColorway / setPlace → state fields updated layoutId, colorwayId, fabricColor, savedPlaces... → scheduleSave() debounce → buildDoc() → API → SQLite → syncScene() or scheduleRebuild() 1 syncPresets() mount/unmount models, applySaved(presets[id]) 2 applySetParams() SET shape (setPresets[id] > drawing defaults) 3 defaultPlaces() SET drawing fills gaps; savedPlaces win 4 applyPlaces() ONE writer of frame coordinates 5 refreshPillarPlaces() pillars re-derive from frame anchors 6 applyPlaces() again, so pillars and frames land together 7 frameScene() camera framing 8 applyPrimaryTheme() then applyColorway() colour beats theme 9 panel.refresh(...) force when the SET converted the sliders

6. Using this page in prompts

Name the control and, when you can, the code face of it — then the change is unambiguous:

  • “In applySetParams, also carry fabric advanced settings…”
  • “The SET row should preview the drawing before committing — touch setLayout.”
  • “Add colour should ask for a name — panel fabricBlock + addFabricColor.”
  • “Pillars should follow frameAnchorOf even in All-at-once.” (they already do — cite it and I’ll check that path)

Anything in doc pills is persistent state; anything named with () is a function you can point at. If a control is not on this page, it does not exist in the code yet — that is a feature request, and a good prompt.
